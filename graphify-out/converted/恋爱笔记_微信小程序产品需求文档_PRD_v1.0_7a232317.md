# 1. 产品定义与目标
## 1.1 一句话定义
恋爱笔记是一款面向成年情侣的私密共同记录微信小程序：两个人可以记录关系中的真实时刻、共同回应、按时间回看，并把一段时期的记忆整理成可保存的作品。
## 1.2 要解决的问题
| 问题 | 现有做法的不足 | 产品解法 |
| --- | --- | --- |
| 记录分散 | 照片、视频、聊天记录分散在相册和聊天中，缺少语境 | 把媒体、感受、时间、事件类型组合成一条“时刻” |
| 只有单方视角 | 普通日记无法自然获得另一半的回应 | 情侣共享空间、回应、共同补充与双人回顾 |
| 回看困难 | 相册按拍摄时间排列，无法按关系阶段和情绪理解 | 天/周/月/年/自定义视角，加事件与心情筛选 |
| 整理成本高 | 年度视频或长图需要手工挑选、排版、配文 | 系统候选、用户确认、模板生成、导出保存 |
| 互动缺乏持续性 | 纪念日提醒短暂，缺少轻量共同目标 | 不惩罚、不排行的双人云宠物和温和任务 |

## 1.3 产品目标
- 低负担记录：首次用户在 2 分钟内完成一条含图片/视频与配文的记录。
- 形成双人闭环：记录可被另一半看见并回应，回应结果沉淀在同一条时刻中。
- 让时间可感知：用户可在 3 次操作内切换到天、周、月、年或自定义范围。
- 可控地生成回顾：系统负责筛选与排版，用户始终拥有内容选择、编辑与删除权。
- 隐私优先：默认不公开、不建立陌生人社交关系、不以分享换取核心功能。
## 1.4 非目标
- 不做陌生人匹配、公开动态广场、粉丝或排行榜。
- 不替代即时聊天工具，不建设实时聊天、语音通话或已读回执。
- 不对关系健康度作医学或心理诊断，不判断争吵中谁对谁错。
- 首版不承诺“任意照片一键生成写实情侣照”；先用可控模板完成美化。
- 首版不做付费体系、会员订阅或实体印刷下单。
## 1.5 核心闭环与北极星指标
|  | 核心闭环 记录一个时刻 -> 另一半查看并回应 -> 双方在时间视图中再次回看 -> 获得回顾/宠物成长反馈 -> 继续记录。 |
| --- | --- |

建议北极星指标：完成配对且最近 30 天共同沉淀不少于 3 条有效时刻的情侣对数。有效时刻指至少包含媒体或 20 字以上文本，且未删除、非失败草稿。
# 2. 用户、场景与设计原则
## 2.1 目标用户
| 用户类型 | 特征 | 核心诉求 |
| --- | --- | --- |
| 主要记录者 | 更愿意拍照、写感受、整理纪念日 | 记录快、作品好看、另一半有回应 |
| 轻参与者 | 不常写长文，但愿意看、回应、照顾宠物 | 操作简单、提醒不过度、有明确参与入口 |
| 回顾型用户 | 平时记录不频繁，在纪念日或年末集中整理 | 系统自动选片、快速生成、允许修订 |
| 未配对用户 | 先试用或尚未邀请成功 | 可以独立记录，配对后自主决定是否共享旧内容 |

首版建议面向 18 岁及以上用户。产品允许记录争吵、和好、“第一次”等关系节点，但不鼓励上传违法、露骨色情、暴力或侵犯他人隐私的内容。
## 2.2 典型使用场景
1. 约会结束后，用户选择 3 张照片，写下当时感受，套用“奶油胶片”边框并发布到情侣空间。
2. 两人发生争执后，一方用纯文字或照片记录事实与感受，并选择“仅自己可见”；和好后可主动转为共同可见。
3. 另一半收到应用内提醒，打开时刻，用表情和一句话回应；回应与原记录一起保存。
4. 月末从月历查看本月记录密度、情绪分布和代表时刻，不把记录数量解释为感情好坏。
5. 周年或年末，系统生成候选回顾，双方可删掉私密或不愉快内容，再输出长图或故事页。
6. 双方完成记录和回应任务后，云宠物获得成长值并解锁装饰，但不会因未登录而生病或死亡。
## 2.3 设计原则
| 原则 | 具体约束 |
| --- | --- |
| 真实而非只甜 | 支持开心、平静、委屈、争执、和好等记录；文案不制造“完美情侣”压力 |
| 私密默认 | 所有内容默认仅本人或当前情侣空间可见；公开分享必须由用户主动发起 |
| 轻记录 | 媒体优先、字段可选、自动保存草稿、失败可续传 |
| 共同但不强迫 | 一方可记录，另一方可轻回应；配对、共享旧记录、订阅提醒均需明确同意 |
| 回忆不被算法篡改 | 生成内容与原始记录区分保存；原图、原文永不被覆盖 |
| 养成不惩罚 | 宠物不死亡、不连续签到绑架、不用情侣间比较刺激活跃 |
| 尊重关系终止 | 任何一方可解绑；解绑后立即撤销对情侣空间中新内容的访问 |

| v1.2 / P1 | 全文搜索、地点足迹、关系时间胶囊、数据导出包、宠物房间装扮 | 月活与回看使用数据证明需求 |

## 3.3 资源不足时的裁剪顺序
按以下顺序从后向前裁剪：宠物装扮扩展 -> 自定义筛选高级项 -> 年度故事动效 -> 视频上传编辑 -> 云宠物。不得裁剪配对、基础记录、共同可见、时间回看、隐私与解绑。
# 4. 信息架构与核心流程
## 4.1 一级信息架构
| 一级入口 | 定位 | 主要页面/能力 |
| --- | --- | --- |
| 时光 | 默认首页与回看中心 | 今日摘要、最近时刻、天/周/月/年/自定义视图、筛选 |
| 记录 | 全局主操作 | 拍摄/选择媒体、写感受、选择属性、图片美化、发布 |
| 我们 | 双人互动空间 | 关系卡、云宠物、共同任务、纪念日、互动消息 |
| 回顾 | 阶段作品 | 年度/周年回顾、生成记录、草稿、导出 |
| 我的 | 个人与安全设置 | 个人资料、可见范围默认值、提醒、存储、隐私、解绑/注销 |

小程序底部建议使用 4 个固定 Tab：“时光”“我们”“回顾”“我的”，中间悬浮“+ 记录”作为全局主按钮。这样既不占用一个纯操作型 Tab，也能强化记录入口。
## 4.2 首次使用流程
| 步骤 | 用户动作 | 系统反馈 | 退出/异常处理 |
| --- | --- | --- | --- |
| 1 | 进入小程序并同意必要协议 | 展示价值说明；按需申请隐私授权 | 不同意则可浏览说明，不创建账号 |
| 2 | 完成微信登录 | 创建用户，进入轻量引导 | 失败可重试，不丢失已选媒体 |
| 3 | 选择“先记录”或“邀请另一半” | 分别进入个人记录或邀请流程 | 以后可在“我们”中继续邀请 |
| 4 | 完成首条记录 | 提示是否共享；未配对时默认仅自己 | 自动保存草稿 |
| 5 | 完成配对 | 展示共享规则，双方确认后创建情侣空间 | 旧记录不会自动共享 |

## 4.3 记录主流程
|  | 主流程 点击“+” -> 选择图片/视频/纯文字 -> 输入感受 -> 选择心情/事件/时间/可见范围 ->（图片可选）进入甜蜜美化 -> 预览 -> 发布 -> 上传完成 -> 对方可见并回应。 |
| --- | --- |

发布操作不应等待长耗时生成。原始记录先入库，模板图片或回顾作品通过独立任务生成；用户可离开页面，失败后从任务中心重试。
## 4.4 配对流程
1. 发起方生成一次性邀请链接/二维码，默认 24 小时有效，可主动撤销。
2. 受邀方打开链接，查看发起方昵称与头像，确认当前账号未处于其他配对关系。
3. 双方阅读共享与解绑规则；受邀方确认后创建情侣空间，发起方收到成功通知。
4. 双方可设置关系昵称、纪念日，并共同领养宠物。旧记录保持原可见范围，由各自手动批量选择共享。
## 4.5 年度回顾流程
1. 选择年份和作品形式；系统检测该年可用记录数量。
2. 系统生成候选章节和素材列表；争吵、委屈、私密标签默认排除。
3. 用户编辑标题、章节、照片顺序和配文，并预览隐私提示。
4. 生成故事页与长图；产物记录版本号，不覆盖原始记录。
5. 用户保存到相册或发起微信分享；分享前再次展示可见内容清单。
# 5. 功能需求
## 5.1 账号、身份与配对
| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| ACC-01 | P0 | 微信身份登录并创建内部用户 ID | 首次授权成功后可进入；同一微信身份重复登录映射同一用户；服务端不信任客户端传入 user_id |
| ACC-02 | P0 | 支持未配对状态独立使用 | 未配对用户可新建、编辑、回看仅自己的记录；共享选项不可选并说明原因 |
| ACC-03 | P0 | 一个账号同一时间只能加入一个有效情侣空间 | 已配对用户打开新邀请时被阻止；服务端并发请求也不会创建重复关系 |
| ACC-04 | P0 | 生成一次性邀请链接/二维码 | 邀请 24 小时后失效；使用后失效；发起方可提前撤销；链接不暴露内部用户 ID |
| ACC-05 | P0 | 接受邀请前展示对方身份与共享规则 | 受邀方必须主动确认；不可替用户自动接受；已失效邀请给出重新邀请入口 |
| ACC-06 | P0 | 关系资料设置 | 双方均可修改关系昵称；纪念日修改记录操作人和时间；日期可留空 |
| ACC-07 | P0 | 解绑可由任一方单独发起 | 二次验证后立即冻结情侣空间并撤销双方互访；不要求对方同意；双方收到应用内通知 |
| ACC-08 | P0 | 解绑后的内容隔离 | 每人仅保留自己创建的记录和自己上传的媒体；对方上传内容立即隐藏；原情侣回顾停止访问 |
| ACC-09 | P0 | 账号注销 | 完成身份校验后进入注销流程；告知影响；按政策删除或匿名化数据，并保留可审计处理状态 |

## 5.2 时刻记录
| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| MOM-01 | P0 | 支持图片、视频、纯文字三类时刻 | 图片 1-9 张；单条时刻不混合图片和视频；视频单个；具体大小/时长由服务端配置并在选择后校验 |
| MOM-02 | P0 | 配文与标题 | 标题可选，最多 30 字；正文最多 1000 字；实时显示剩余字数；保留换行 |
| MOM-03 | P0 | 记录发生时间 | 默认当前时间；允许回填过去时间；未来时间不可超过 5 分钟；排序使用发生时间而非创建时间 |
| MOM-04 | P0 | 心情标签 | 单选：开心、心动、平静、想念、委屈、生气、和好、其他；可不选；统计不得把标签解释为关系评分 |
| MOM-05 | P0 | 事件标签 | 多选不超过 3 个：日常、约会、旅行、纪念日、第一次、争执、和好、礼物、共同成长、其他 |
| MOM-06 | P0 | 可见范围 | 仅自己/情侣共同可见；未配对仅能选“仅自己”；默认沿用用户设置但发布前清晰展示 |
| MOM-07 | P0 | 草稿与失败恢复 | 输入 3 秒内自动保存本地草稿；退出可继续；上传失败保留本地选择和已上传资源引用，可单项重试 |
| MOM-08 | P0 | 发布状态 | 草稿、上传中、已发布、部分失败、已删除；上传未完成时在时间线显示仅作者可见的进度卡 |
| MOM-09 | P0 | 编辑 | 作者可编辑配文、标签、发生时间、可见范围；已共享转仅自己前提示将使对方无法再访问 |
| MOM-10 | P0 | 软删除与恢复 | 删除进入回收站 30 天；作者可恢复；到期异步物理删除媒体；共享内容删除后对方立即不可见 |
| MOM-11 | P0 | 媒体元信息处理 | 服务端生成缩略图；默认不向对方/导出图暴露设备、GPS 等 EXIF 信息；原媒体与展示版本分离 |
| MOM-12 | P1 | 另一半补充“TA 的视角” | 双方可向同一时刻添加自己的文本与媒体；每份媒体保留独立上传者和删除权 |

## 5.3 图片甜蜜美化
首版定义为“模板合成”，而非不可控的写实生成。模板合成可在小程序 Canvas 或服务端渲染，输出结果稳定、成本可控，也更容易通过隐私与内容审核。
| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| IMG-01 | P0 | 提供至少 6 套风格模板 | 建议：奶油胶片、草莓手账、月光蓝、复古拍立得、旅行邮票、极简纪念；模板由后台配置上下线 |
| IMG-02 | P0 | 模板元素 | 支持边框、背景色/纹理、滤镜、日期、标题/配文、贴纸；所有元素有安全区，文字不遮挡主要人物区域 |

## 6.2 时刻卡规格
- 卡片必须展示：发生日期/时间、作者身份、媒体封面或文字摘要、可见范围（仅作者可见时）、上传/生成状态。

- 争执或委屈记录使用中性色，不使用破碎爱心、红色警报等戏剧化视觉。
- 长按不承担唯一操作入口；编辑、删除等必须在详情页菜单中可达。

## 6.5 无障碍与易用性
- 正文与关键操作文字不小于可读基线；支持系统字体放大时不截断核心按钮。
- 颜色不作为唯一状态提示；上传失败、可见范围、选中状态均配文字或图标。
- 点击热区不小于常见移动端可用尺寸；重要操作不依赖滑动手势。
- 视频默认静音预览，用户主动播放；动效支持减少动画的降级方案。
- 图片上的配文同时保存在结构化文本中，避免内容只存在于图片像素内。
# 7. 业务规则与状态
## 7.1 情侣关系状态
| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| UNPAIRED | 未配对 | 个人记录、创建邀请 |
| INVITING | 有未使用邀请 | 个人记录、撤销/重发邀请；仍视为未配对 |
| PAIRED | 有效情侣空间 | 共享记录、互动、宠物、双人回顾 |
| FROZEN | 解绑处理中/已冻结 | 仅访问个人可保留内容；禁止新增共享与互动 |
| ENDED | 关系已结束且数据分离完成 | 重新邀请；不可访问旧情侣空间 |

## 7.2 时刻状态
| 状态 | 进入条件 | 退出条件 | 可见性 |
| --- | --- | --- | --- |
| DRAFT | 用户开始编辑 | 发布或删除草稿 | 仅本机/本人 |
| UPLOADING | 提交发布且媒体上传中 | 全部成功、部分失败或取消 | 仅作者 |
| PUBLISHED | 文本与必要媒体处理成功 | 编辑、删除、解绑权限变化 | 按 visibility |
| PARTIAL_FAILED | 部分媒体失败 | 重试成功或移除失败项 | 仅作者，确认后可降级发布 |
| TRASHED | 作者删除 | 30 天内恢复或到期清理 | 仅作者回收站 |
| PURGED | 物理清理完成 | 终态 | 不可见 |

## 7.3 可见范围与归属规则
|  | 推荐的归属模型 记录归创建者；媒体归上传者；情侣空间只授予关系存续期间的访问权，不自动转移所有权。解绑时按创建者/上传者拆分，是实现隐私隔离与数据删除的基础。 |
| --- | --- |

| 对象 | 所有者 | 关系存续期 | 解绑后 |
| --- | --- | --- | --- |
| 时刻主记录 | 创建者 | shared 时双方可见；private 时仅创建者 | 创建者保留；对方不可见 |
| 媒体 | 上传者 | 随所属记录和可见范围授权 | 上传者保留；非上传者不可见 |
| 回应/短评 | 发表者 | 双方可见 | 发表者可在个人操作记录中删除；不向对方继续展示 |
| 云宠物 | 情侣空间 | 双方共同使用 | 冻结，仅生成不含对方媒体的结束纪念卡 |
| 双人回顾 | 情侣空间派生产物 | 双方可见和编辑 | 停止访问；个人可重新用自己的素材生成个人回顾 |

## 7.4 并发与幂等
- 配对接受、解绑、宠物互动、成长结算、生成任务创建必须使用服务端幂等键或唯一约束。
- 同一账号多设备编辑同一时刻时使用 version 字段做乐观锁；冲突提示用户刷新，不静默覆盖。
- 媒体上传完成回调必须验证文件归属、任务状态与签名，重复回调不重复创建资产。
- 时间视图分页采用稳定游标，不使用会因新增内容漂移的单纯 offset。

| /auth | 登录、会话刷新、注销 | 服务端换取并绑定身份；会话过期可恢复当前草稿 |
| /couples | 邀请、接受、关系资料、解绑 | 事务与唯一约束；所有写请求审计 |
| /moments | 创建、编辑、分页、详情、删除、恢复 | 统一权限中间件；游标分页；乐观锁 |
| /uploads | 获取上传凭证、完成确认、缩略图状态 | 白名单格式/大小；短期凭证；回调校验 |
| /interactions | 回应、短评、消息 | 幂等；只对可访问时刻开放 |
| /pets | 领养、互动、状态、日志 | 日限额、服务端时间、幂等结算 |
| /recaps | 候选、草稿、生成、进度、导出 | 输入快照、版本化、异步任务 |
| /privacy | 导出、回收站、授权与操作记录 | 身份校验、最小披露、到期清理 |

## 8.3 媒体处理链路
1. 客户端向服务端申请短期上传凭证，服务端返回 storage_key 和限制条件。
2. 客户端直传对象存储并上报完成；服务端校验类型、大小、哈希和所有者。
3. 异步执行内容安全检测、缩略图/视频封面生成和必要转码。
4. 通过后资产进入 READY；不通过进入 BLOCKED；处理中仅作者可见进度。
5. 时间线只使用缩略图和自适应资源；原媒体通过鉴权后的短期地址访问。
## 8.4 技术实现建议（非强制）
- 小程序端：使用团队成熟的原生框架或跨端框架；关键是稳定支持媒体选择、Canvas 合成、分包与性能监控。
- 服务端：关系/权限/记录使用关系型数据库；媒体使用对象存储与 CDN；生成任务使用消息队列和独立 Worker。
- 图片模板：采用 JSON 描述布局、字体、颜色、安全区和素材版本，避免每套模板都发版。
- 视频回顾：后续采用服务端渲染，不依赖小程序前台长时间运行。
- AI 服务：必须经过服务端代理，隐藏密钥，并支持供应商切换、成本配额、输入删除策略和审计。

## 9.1 微信小程序约束
- 登录、媒体选择、相册保存、订阅消息等能力均按开发时微信官方最新接口、隐私规范和审核要求实现。
- 外部提醒不得假设可以长期无限推送；产品必须在没有外部提醒时仍可通过应用内消息完整使用。
- 媒体大小、时长、格式和基础库兼容范围由研发在技术设计阶段验证，并通过服务端配置落地。
- 分享只是导出路径，不应通过分享链接绕过情侣空间权限；公开分享产物应与私密详情页分离。

# 11. 验收、发布与迭代
## 11.1 MVP 业务验收清单
□ 新用户可不配对完成首条记录，退出重进后内容仍在。
□ 邀请可创建、撤销、过期、接受；并发接受不会产生多个有效情侣空间。
□ 图片、视频、纯文字均可发布；断网、失败、重试和草稿恢复路径完整。
□ 仅自己内容不会通过时间线、消息、旧链接或回顾泄露给另一半。
□ 天/周/月/年/自定义视图的数量与详情一致，跨年和时区边界正确。
□ 至少 6 套图片模板在目标设备上无文字截断、图片变形和清晰度异常。
□ 回应、短评、应用内消息权限正确；删除后不留可访问的媒体永久链接。
□ 云宠物操作幂等、日限额正确、等级不倒退、无惩罚性断签表现。
□ 年度回顾默认排除私密与敏感记录，编辑和导出结果一致。
□ 任一方解绑后立即无法访问对方记录、媒体、互动详情与旧回顾。
□ 回收站、账号注销、隐私授权、内容反馈链路可用并有审计记录。
□ 弱网、低存储、低端机、后台切换、重复点击等异常场景完成真机测试。
## 11.2 建议项目节奏
| 阶段 | 建议周期 | 主要产出 | 退出条件 |
| --- | --- | --- | --- |

## 11.3 发布门槛
- P0 需求验收通过，P0 缺陷清零，P1 高影响缺陷有明确规避方案。
- 隐私保护指引、用户协议、内容规范、注销与投诉入口完整，并与实际收集字段一致。
- 越权、解绑、旧链接、对象存储访问、生成任务输入等安全用例全部通过。
- 完成小范围灰度：至少覆盖新用户、未配对、已配对、解绑、弱网和不同机型。
- 监控、告警、回滚、配置开关、内容处理和客服响应流程可用。
# 12. 风险与待决策事项
## 12.1 主要风险
| 风险 | 影响 | 建议措施 |
| --- | --- | --- |
| 隐私泄露/越权 | 最高：造成信任与合规事故 | 服务端统一权限中间件；短期媒体地址；解绑专项测试；不以客户端隐藏代替鉴权 |
| 生成式 AI 结果不可控 | 人物变形、审美不稳定、成本和审核压力 | MVP 仅模板合成；AI 作为可选 P1；保留原图、标记 AI、配额与审核 |
| 年度回顾触发负面情绪 | 自动加入争吵或私密内容造成伤害 | 敏感标签默认排除；逐条确认；不生成关系评分和价值判断 |
| 云宠物变成活跃压力 | 用户反感、情侣间比较 | 不死亡、不降级、不显示贡献排行榜、不做连续签到惩罚 |
| 媒体成本增长 | 存储、CDN、转码和生成成本不可控 | 大小/时长配置、缩略图优先、冷热分层、配额、单位成本监控 |
| 配对/解绑争议 | 数据归属不清导致投诉 | 配对前明确规则；记录/媒体分属；单方可解绑；关键操作审计 |
| 小程序审核或接口变化 | 上线延迟或能力受限 | 开发前做能力验证；外部提醒/分享均有应用内降级路径 |
