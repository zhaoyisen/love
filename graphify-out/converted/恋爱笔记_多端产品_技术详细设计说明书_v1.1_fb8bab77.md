# 1. 设计目标、范围与约束
## 1.1 设计目标
- 把 PRD 中的 P0 能力落实为可编码、可联调、可测试、可运维的技术方案。
- 确保私密默认、关系存续期授权、单方解绑即时隔离三条底线由服务端强制执行。

# 3. 总体架构设计
## 3.1 架构原则
- 权限先于数据：任何详情、列表、媒体和派生物查询都先形成服务端授权范围，禁止客户端全量拉取后过滤。
- 原始内容不可覆盖：模板图、缩略图、回顾长图均是派生资产，保存 source_asset_id 与版本。
- 写路径可重放：创建邀请、接受配对、发布、回应、宠物动作、生成、解绑都支持幂等键。
- 事务内只做关键状态变更：耗时审核、转码、渲染、删除由 Outbox 可靠投递到 Worker。
- MVP 采用模块化单体，不提前拆微服务；按业务域隔离包、表访问与事件，达到规模后再独立部署。
- 配置而非硬编码：媒体限制、模板、宠物成长、生成配额、开关和审核策略进入配置中心。
- 前后端分离：客户端不直连数据库、对象存储管理接口或第三方密钥；业务状态以统一服务端为事实源。
- 多端同域：小程序与 App 共用领域模型和 API 契约；只允许渠道适配差异，不复制关系、权限和内容规则。
## 3.2 推荐技术基线
| 层 | 推荐 | 理由/约束 |
| --- | --- | --- |
| 多端客户端 | 微信小程序 + iOS/Android 独立 App；UI 与端能力独立实现 | 同一产品与数据域；不假设跨端共享 UI 代码；统一接口契约 |
| API 契约 | OpenAPI 3.x + 生成式 TypeScript/Swift/Kotlin/Dart SDK（按 App 技术栈） | 服务端模型单一来源；客户端 DTO 不手工漂移 |
| 统一 API 服务 | Java 21 LTS + Spring Boot 3.x + Bean Validation | 模块化单体；同时服务 MiniProgram/iOS/Android；不按端复制业务服务 |
| 持久化 | MySQL 8.0 InnoDB + SQL Mapper | 多端共享用户、关系、时刻、互动、宠物与回顾数据 |
| 缓存 | Redis 7 | 会话、频控、幂等和缓存按用户/资源维度，不按端分裂事实 |
| 异步 | 托管消息队列 + Outbox Publisher + Worker | 统一处理审核、转码、渲染、删除和多渠道通知 |
| 媒体 | 私有对象存储 + 鉴权 CDN + 图片/视频处理 | 各端统一使用 upload_session；端侧直传但授权由服务端签发 |
| 交付与质量 | 客户端独立流水线 + 服务端容器化 + 契约/兼容/E2E/SAST | 环境一致；旧客户端兼容窗口；可独立灰度和回滚 |

## 3.3 逻辑架构
- 统一服务端原则：所有客户端使用同一用户、情侣关系、权限、时刻、媒体、互动、宠物、回顾和审计数据；任何端都不得维护可分叉的服务端业务副本。
- 渠道适配原则：微信 code、App 登录、APNs/Android 厂商推送、订阅消息、Universal Link/App Link 和小程序分享只进入 channel adapter。
- 契约兼容原则：统一 API 只做向后兼容演进；Client-Channel、Client-Version、Device-Id 用于能力协商、灰度和问题追踪，不用于改变核心权限。

| 组件 | 部署建议 | 高可用/扩展策略 |
| --- | --- | --- |
| API | 统一 API 至少 2 副本，无状态，置于网关/WAF 后；按 ClientChannel 观测，不拆端专属业务服务 | 按 CPU、P95、请求数水平扩容；发布采用小流量灰度 |
| Worker | 审核、媒体、渲染、清理可同镜像不同消费组 | 按队列积压和最老消息年龄扩容；任务租约防重复执行 |
| MySQL | 主库 + 同地域高可用；只读副本后置 | 关系/权限强一致读主库；报表可读副本 |
| Redis | 主从/集群托管版 | 缓存可丢；会话和限流需持久化/高可用策略 |
| 对象存储 | private-original / private-derived 逻辑前缀或独立桶 | 版本、生命周期、跨区域容灾按合规与成本确认 |

| 通知适配器 | 同一领域事件分发应用内消息、微信订阅消息、APNs/Android 厂商推送 | 渠道熔断和独立重试；外部推送失败不影响业务事务 |

# 4. 多端客户端详细设计
## 4.1 客户端组织与代码边界
- 前后端分离边界：客户端负责展示、交互、本地草稿、上传编排和渠道能力调用；服务端负责身份、权限、业务状态、数据、审计和异步任务。
- 客户端独立发布：小程序审核、App Store 和 Android 渠道节奏不同，服务端必须允许多个客户端版本同时在线。
- 契约单一来源：OpenAPI、枚举和错误码从服务端生成；客户端不得复制权限判断作为安全边界。

## 4.3 草稿、请求与本地数据
- 本地草稿键：draft:{userPublicId}:{draftId}；值包含 schema_version、updated_at、字段、媒体临时路径和已上传 asset_id。
- 小程序启动时先恢复 session，再扫描当前用户草稿；用户切换或注销必须隔离/清除其他账号草稿。
- 所有写请求生成 UUID idempotency_key；页面重复点击复用同一 key，直到获得确定结果或用户明确重新发起。
- 请求层统一注入 request_id、access_token、client_version、timezone；401 只自动刷新一次，仍失败回登录。
- 本地不持久化 signed_url、session_key、openid、内容安全原始结果或对方不可见数据。
- 弱网下允许保存草稿；发布需联网。上传完成但发布失败时保留 asset_id，以便恢复并避免重复上传。

- 可见范围始终显示完整文案；颜色不作为唯一状态。共同可见需 active couple，发布前再次呈现。
- 敏感操作按钮热区不小于移动端可用基线；支持系统字体放大；重要操作不依赖长按/滑动。

- 埋点只发送匿名业务 ID、枚举、数量、时长桶和结果；正文、标签明细、媒体地址和邀请 token 禁止上报。

## 4.7 多端兼容与发布策略
- 每次请求携带 Client-Channel、Client-Version、Platform-Version 和 Device-Id；服务端基于能力矩阵返回 feature_flags，不使用渠道字段改变资源权限。
- API 字段采用只增不破坏策略；删除/改义至少经过弃用、双写/双读、最低版本门槛和存量版本占比确认。
- 小程序与 App 分别灰度；服务端开关可按用户、渠道、版本、灰度桶控制，但同一资源状态对所有端保持一致。
- 本地草稿用 user_id + client_channel + installation_id 隔离；发布成功后所有端通过统一时间线读取同一时刻。
# 5. 服务端详细设计
## 5.1 应用分层
| 层 | 职责 | 规则 |
| --- | --- | --- |
| API/Controller | 协议转换、参数校验、鉴权上下文、request_id | 不写业务事务；不返回内部异常栈 |
| Application | 用例编排、事务边界、幂等、授权调用、Outbox | 一个命令对应清晰事务；跨模块使用接口/事件 |
| Domain | 关系、时刻、宠物、回顾的状态与不变量 | 无 HTTP/存储细节；状态迁移集中定义 |
| Infrastructure | SQL、Redis、对象存储、微信、队列、审核供应商 | 第三方响应映射为内部错误；支持替换 |
| Worker | 拉取任务、租约、心跳、进度、重试、补偿 | 至少一次执行；业务动作必须幂等 |

## 5.2 统一鉴权与授权
身份认证只解决“是谁”，资源授权解决“是否能做”。Controller 解析会话后生成 ActorContext；所有领域查询必须接受 ActorContext 或由仓储接收已计算的 AccessScope。
| AccessScope resolve(actor, resourceType, action): require actor.status == ACTIVE if resourceType == MOMENT: allow owner action when moment.author_id == actor.user_id allow read/interact when moment.visibility == SHARED and moment.couple_id == actor.active_couple_id and couple.status == PAIRED if resourceType == MEDIA or RECAP: derive permission from parent record/snapshot, never from URL possession deny by default; record structured denial reason; do not disclose resource title |
| --- |

## 5.3 事务与事件
- 数据库事务覆盖业务状态、唯一约束、审计记录和 outbox_event 写入；外部对象存储/队列调用不放在事务内。
- Outbox Publisher 按主键游标扫描 NEW 事件，发送成功后标记 SENT；崩溃可重复发送，消费者按 event_id 去重。
- 解绑、注销、删除等事件必须带 effective_at 和 relation_version，Worker 处理前再次确认当前版本，防止旧事件覆盖新状态。
- 所有命令返回 resource_version；更新请求使用 If-Match 或 body.version，版本不一致返回 409 VERSION_CONFLICT。
## 5.4 身份与会话
1.  小程序使用微信临时 code；App 使用经确认的登录方式（Apple/微信开放平台/手机号等）。所有渠道统一调用身份会话域，不直接创建业务用户。
2.  user 表只表示业务用户；user_identity 以 provider + provider_subject_hash 唯一关联外部身份，敏感标识加密并与业务资料隔离。
3.  首次登录创建内部 user_id；已登录用户绑定新身份必须进行近期认证，防止把两个业务账号静默合并。账号合并另设人工/可回滚流程。
4.  access token 只含 user_id、session_id、session_version、channel 和过期时间；refresh token 只存哈希并轮换。不同端会话可分别吊销。
5.  device_installation 记录渠道、平台、应用版本、推送 token 密文/哈希和最后活跃时间；卸载、换 token、退出或注销时撤销。

# 6. 数据设计
## 6.1 通用规范
- 主键使用 UUIDv7，数据库存 BINARY(16)，API 使用规范字符串；排序同时使用业务时间、created_at、id。
- 所有时间以 UTC datetime(3) 保存，API 使用 ISO 8601；请求携带 timezone，日/周/月边界由服务端计算。
- 业务表包含 created_at、updated_at；可编辑聚合包含 version；软删除用 deleted_at/status。
- 枚举在代码和 OpenAPI 中统一；未知枚举客户端降级展示，避免新值导致崩溃。
- 正文按产品上限保存，不在通用日志/缓存 key/消息正文出现；必要索引不得包含明文正文。

# 7. 状态机与一致性
## 7.1 情侣关系状态机
关系状态
| 当前状态 | 触发事件 | 下一状态 | 关键原子动作 |
| --- | --- | --- | --- |
| UNPAIRED | 创建有效邀请 | INVITING | 写 invitation=ACTIVE；不创建成员绑定 |
| INVITING | 撤销/过期 | UNPAIRED | invitation=REVOKED/EXPIRED |
| INVITING | 受邀方确认 | PAIRED | 锁邀请和双方用户；写 couple + 两条 active_member + audit + outbox |
| PAIRED | 任一方确认解绑 | FROZEN | 锁 couple；status=FROZEN；删除 active_member；撤销邀请；写审计/outbox |
| FROZEN | 隔离任务完成 | ENDED | 冻结宠物/回顾；清理授权缓存；生成完成记录 |
| ENDED | 重新邀请 | INVITING | 旧 couple 不复用，创建新 invitation |

| 强一致点 解绑 API 返回成功前必须提交 FROZEN 和 active_couple_member 删除。媒体、时刻、互动、回顾的授权查询同时检查 active membership 与 couple.status，因此旧链接在事务提交后立即失效，不依赖异步清理。 |
| --- |

## 7.2 时刻状态机
时刻状态
| 当前状态 | 触发事件 | 下一状态 | 关键原子动作 |
| --- | --- | --- | --- |
| DRAFT | 提交发布 | UPLOADING | 创建 moment + media rows；author only |
| UPLOADING | 全部资产 READY 且文本通过 | PUBLISHED | 设置 published_at；发 outbox；SHARED 才通知对方 |
| UPLOADING | 部分媒体失败 | PARTIAL_FAILED | 保留成功资产和失败原因；仅作者 |
| PARTIAL_FAILED | 重试成功 | PUBLISHED | 幂等确认资产；发布事件只发一次 |
| PARTIAL_FAILED | 移除失败项并确认 | PUBLISHED | 校验仍满足类型/数量；记录降级发布审计 |
| PUBLISHED | 作者编辑 | PUBLISHED | version+1；可见范围收紧后立即撤权 |
| PUBLISHED | 作者删除 | TRASHED | deleted_at；对方立即不可见；取消未开始生成 |
| TRASHED | 30 天内恢复 | PUBLISHED | 重新校验关系；原 SHARED 若关系失效则恢复 PRIVATE |
| TRASHED | 到期清理 | PURGED | 异步删除派生物和对象；保留最小审计 |

## 7.4 幂等与并发
| 场景 | 幂等键/唯一约束 | 冲突处理 |
| --- | --- | --- |
| 邀请创建 | user_id + client_key；同一用户最多一个 ACTIVE | 返回已有邀请或显式替换 |
| 接受配对 | invitation_id；active_member.user_id PK | 事务锁；第二请求返回已处理/已配对 |
| 发布时刻 | author_id + idempotency_key | 返回同一 moment；不重复通知/奖励 |
| 回应 | moment_id + user_id UNIQUE | PUT 语义修改；删除幂等 |
| 宠物动作 | pet + actor + date + action UNIQUE | 重复请求返回原结算 |
| 生成 | type + input + version + params_hash UNIQUE | 复用任务；失败重试增加 attempt，不重复收费 |
| 更新 | resource.version 乐观锁 | 409，返回 current_version，不静默覆盖 |
| 上传回调 | upload_session_id + object etag | 重复回调只更新一次；不重复建资产 |

# 8. 权限与隐私隔离设计
## 8.1 权限矩阵
| 操作 | 作者 | 当前另一半 | 旧链接/未登录 | 解绑后对方 |
| --- | --- | --- | --- | --- |
| 查看 PRIVATE 时刻 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 查看 SHARED 时刻 | 允许 | PAIRED 且同 couple 允许 | 拒绝 | 拒绝 |
| 编辑/删除时刻 | 允许，需 version | 拒绝 | 拒绝 | 拒绝 |
| 获取媒体 URL | 按记录权限 | PAIRED + SHARED | 拒绝 | 拒绝 |
| 回应/短评 | 允许 | PAIRED + SHARED | 拒绝 | 拒绝 |
| 删除互动 | 仅自己的 | 仅自己的 | 拒绝 | 拒绝 |
| 编辑情侣回顾 | PAIRED | PAIRED | 拒绝 | 拒绝 |
| 宠物互动 | PAIRED | PAIRED | 拒绝 | FROZEN/ENDED 拒绝 |
| 解绑 | 单方允许 + 二次确认 | 单方允许 + 二次确认 | 拒绝 | 不适用 |

## 8.2 资源访问判定
1.  按公共 ID 查询最小资源元数据，不在 404/403 响应中泄露标题、作者或是否存在。
2.  校验用户 ACTIVE、会话有效；敏感写操作再校验近期认证与风控状态。
3.  作者权限优先；非作者必须同时满足 SHARED、couple_id 一致、active_member 存在、couple.status=PAIRED。
4.  媒体与派生物从父资源继承授权，signed URL 有效期短且不可跨资源复用；URL 过期需重新鉴权。
5.  授权失败记录 action、resource_type、reason_code、request_id；禁止记录正文、token、storage_key 完整值。
## 8.3 解绑隔离
| 对象 | 事务提交后立即 | 异步完成 |
| --- | --- | --- |
| 时刻 | 对方查询因 membership/status 失败；创建者仍可访问自己记录 | 将失效 SHARED 记录归档为创建者视图，清理缓存 |
| 媒体 | 签发 URL 失败；旧短期 URL 等待极短 TTL 自然过期 | 删除无所有权副本/缓存；保留上传者资产 |
| 互动 | 详情不再返回对方回应/短评 | 按产品规则做个人操作记录最小保留或删除 |
| 宠物 | status=FROZEN，不可操作 | 生成不含对方媒体的结束纪念卡；保持冻结 |
| 情侣回顾 | 访问和导出拒绝 | 冻结/删除可下载产物；个人可用自己的素材新建个人回顾 |
| 邀请/消息 | 撤销相关邀请，不再投递情侣事件 | 发送双方解绑通知，清理未读聚合 |

## 8.4 安全缓存原则
| 禁止项 不得缓存“用户可以访问资源”的长期正向结论。关系/可见范围变化时，授权必须立刻收敛。详情缓存按 resource_version 缓存非敏感主体，返回前重新做轻量授权；signed URL TTL 建议 5 分钟以内并可按风险降低。 |

# 9. 关键流程设计
## 9.1 登录与会话恢复
| 步 | 调用方 | 动作 | 失败处理 |
| --- | --- | --- | --- |
| 1 | 客户端 | 按渠道取得登录凭证：小程序 code；App provider token/code | 失败可重试；不清空当前 installation 草稿 |
| 2 | 统一 API | channel adapter 校验凭证，按 provider + subject 解析 user_identity | 第三方超时映射 AUTH_PROVIDER_UNAVAILABLE；不创建重复用户 |
| 3 | 统一 API | 创建共享业务 session、access/refresh，绑定 channel 与 installation | refresh token 只存哈希；不同设备可分别吊销 |
| 4 | 客户端 | 加载 profile、active couple、feature flags、媒体限制与能力矩阵 | 部分配置失败使用上次非敏感缓存；核心权限仍查服务端 |
| 5 | 客户端 | 按 user + channel + installation 恢复草稿，进入当前端可达页面 | 无权限或当前端不支持时进入通用失效/降级页 |

## 9.2 时刻发布与媒体处理
1.  小程序为每个媒体创建本地 item，申请 upload_session；API 校验 MIME、数量、用户配额并返回短期凭证和 storage_key。
2.  小程序直传私有对象存储并调用 complete；API 验证对象大小、ETag/hash、所有者和 session 状态。
3.  用户点击发布时提交 moment 字段、asset_id 列表、draft_id 和 idempotency_key。API 校验标签、发生时间、可见范围，创建 UPLOADING moment。
4.  Outbox 投递 TEXT_SCAN/MEDIA_PROCESS；Worker 做文本/媒体安全检测、EXIF 清理、缩略图/视频封面/必要转码。
5.  全部必要资产 READY 后状态变 PUBLISHED；若 SHARED 且关系仍 PAIRED，创建消息并结算奖励。部分失败进入 PARTIAL_FAILED。
6.  图片模板任务独立于原始发布；成功后写 derivative_asset。失败不回滚时刻，用户可重试或继续使用原图。
| 关键补偿： - 对象已上传但未 complete：24h 后清理 orphan object。 - complete 已确认但 moment 未创建：资产保持 owner-only，7d 后清理或被草稿复用。 - moment 已创建但队列未收到：Outbox 扫描重新投递。 - Worker 成功但回写超时：按 job/input 唯一键重入并比对产物 hash。 |
| --- |

## 9.3 邀请接受与单方解绑
接受配对事务：
1.  按 token_hash 查询并 FOR UPDATE 锁定邀请；校验 ACTIVE、未过期、未被自己接受。
2.  按稳定顺序锁定双方 user；检查 active_couple_member 均不存在且账号可用。
3.  创建 couple_space=PAIRED 和两条 active_couple_member；邀请标记 ACCEPTED。
4.  写 audit_log 与 outbox_event；提交后返回 couple 公共信息。并发第二事务因状态/唯一键返回已处理。
解绑事务：
1.  校验确认词、近期认证、当前 active couple 和 version；锁定 couple。
2.  couple.status=FROZEN，写 ended_at/initiator；删除两条 active_member；撤销 ACTIVE 邀请。
3.  写 audit_log、UNBIND_STARTED outbox；提交后清除双方授权缓存并返回 FROZEN。
4.  Worker 冻结宠物/回顾、整理个人可保留视图、发送应用内通知；完成后设 ENDED。失败不恢复访问，仅告警并继续补偿。
## 9.4 时间线查询
1.  服务端根据 actor 读取 active couple；标准化 view_type、时间边界、筛选并计算 query_hash。
2.  分别构建本人范围与当前情侣共享范围 SQL，在数据库内过滤 status/visibility/deleted_at。
3.  UNION ALL 后按 occurred_at、created_at、id 倒序，应用带 HMAC 的稳定游标。
4.  批量加载 tags、READY 缩略图、回应摘要；避免 N+1；不生成原件 URL。
5.  周/月/年摘要使用同一 AccessScope 与时间边界，短期缓存按 actor_scope_hash + filters；写事件精确失效。
## 9.5 宠物互动
1.  API 以服务端当前业务日期结算，校验 couple=PAIRED、pet=ACTIVE 和动作开关。
2.  在事务内插入 pet_action 唯一记录；重复键读取原结果并返回 idempotent=true。
3.  根据 rule_version 写 growth_ledger，更新 pet 聚合 growth/level/version；等级只增不降。
4.  写 outbox 供动画/消息使用；客户端动画失败不回滚成长值。
## 9.6 年度回顾生成
1.  候选服务查询自然年内有权限的 PUBLISHED/SHARED 时刻；硬排 private，软排敏感标签。
2.  用户编辑后保存 recap_snapshot vN；每个 item 保存时刻/资产版本和文案快照。
3.  创建 generation_job，唯一键 recap_id + snapshot_version + format + params_hash；返回 job_id。
4.  Worker 校验授权/快照完整性，下载私有资产，渲染故事页/长图，分页并上传 derived 区域。
5.  成功写 READY 产物与 disclosure_manifest；失败保留 error_code 并允许原任务重试。
6.  导出/分享前再次检查当前权限和披露清单；获取短期下载 URL，保存相册由用户主动触发。

## 11.2 上传校验与安全处理
- 申请凭证时校验声明 MIME/大小；complete 时读取对象头和魔数复核，拒绝扩展名伪装。
- 图片做解码炸弹/异常尺寸限制；视频校验容器、编码、时长、分辨率；文件名不进入 storage_key。
- 原件和展示副本分离；对方/导出只访问剥离 EXIF 的展示副本，GPS 等元数据不传播。
- 安全检测前对象在 quarantine/processing 权限域；BLOCKED 不生成缩略图公开 URL，不进入回顾。
- 服务端回调必须验签并校验 upload_session、object key、owner、状态；重复回调幂等。
- 对象删除采用 tombstone + 重试队列；数据库先撤权，再异步删除物理对象，失败持续告警。

## 11.4 回顾渲染
- Worker 只从 recap_snapshot 读取输入，防止生成中原记录修改导致前后不一致。
- 长图按最大像素/文件大小自动分页；故事页输出结构化页面数据和展示图，均记录 renderer_version。
- 字体、贴纸和曲库等资产必须有授权来源和版本；渲染镜像固定依赖并生成可追踪构建号。
- 产物生成后复核页数、尺寸、空白页、文本溢出、缺图；不通过则任务失败而非发布损坏产物。
- 导出前重新生成披露清单；若权限或源状态改变，标记 snapshot stale，要求用户重新确认。
# 12. 缓存、消息与后台任务
## 12.1 Redis 使用
| 用途 | Key 示例 | TTL/一致性 |
| --- | --- | --- |
| 会话 | sess:{session_id} | 与 refresh 周期一致；注销/强退删除 |
| 频控 | rate:{actor}:{action}:{window} | 窗口 TTL；服务端时间 |
| 幂等结果 | idem:{actor}:{method}:{path}:{key} | 24h 或业务要求；DB 唯一约束为最终保障 |
| 配置 | cfg:{domain}:{version} | 短 TTL + 发布事件失效 |
| 详情主体 | moment:{id}:v{version} | 不含 signed URL；返回前授权 |
| 时间摘要 | summary:{scope_hash}:{range}:{filter_hash} | <=60s + 写事件精确失效 |
| 任务进度 | job:{id}:progress | 短 TTL；最终状态写 DB |

## 12.2 缓存失效
- moment 发布/编辑/删除/可见范围变化：失效作者和当前情侣的相关详情与日期摘要。
- couple FROZEN/ENDED：失效双方 active couple、所有授权 scope 和共享摘要；拒绝优先于缓存命中。
- reaction/comment：失效 moment 互动摘要和消息未读数，不失效媒体主体。
- recap/version/job：按 recap_id/version 更新；产物 URL 从不缓存为业务数据。
- 缓存失效失败由 outbox 重试；安全场景同时使用短 TTL 和数据库状态校验。
## 12.3 任务模型
| 任务 | 超时/重试建议 | 失败终态 |
| --- | --- | --- |
| TEXT_SCAN | 短超时，指数退避 3 次 | BLOCKED/FAILED；作者可见提示 |
| IMAGE_PROCESS | 按大小，3 次 | MediaAsset FAILED，支持重试 |
| VIDEO_PROCESS | 长租约 + 心跳，2 次 | PARTIAL_FAILED/DLQ |
| TEMPLATE_RENDER | 按模板复杂度，2 次 | Derivative FAILED，不影响原记录 |
| RECAP_RENDER | 长租约 + 进度，2 次 | Recap FAILED，可原任务重试 |
| PURGE_OBJECT | 持续退避，直到保留期上限 | 告警 + 人工工单；访问已撤销 |
| UNBIND_FINALIZE | 持续重试，步骤可幂等 | 保持 FROZEN，绝不恢复互访 |

## 12.4 消息与通知
- 应用内消息是所有客户端的统一事实源；新时刻、回应、短评、宠物、回顾、解绑由同一领域事件生成，安全通知不可关闭。
- notification dispatcher 根据 device_installation 和用户偏好路由：微信小程序订阅消息、iOS APNs、Android 厂商推送；渠道失败不回滚业务。
- 同类消息按 aggregate_key 聚合；payload 只含类型、资源公共 ID 和显示快照，不含正文、媒体 URL 或可绕过鉴权的深链参数。
- 深链统一使用服务端生成的 link_target（resource_type + public_id）；各端解析后仍调用统一详情 API 鉴权。已读状态仅属于当前用户，不向另一方暴露。
# 13. 安全、隐私与合规设计
## 13.1 威胁模型
| 威胁 | 控制 |
| --- | --- |
| 枚举公共 ID/旧链接越权 | UUIDv7 不可猜 + 统一授权 + 通用 403/404 + 速率限制 |
| 客户端伪造 user_id/couple_id | 身份来自服务端会话；couple 从 active_member 推导 |
| 对象存储泄漏 | 私有桶、最小权限、短期 URL、无永久公开地址、访问日志 |
| 邀请 token 泄漏 | 随机高熵 token，只存 hash，24h、一次性、可撤销、速率限制 |
| 上传恶意文件 | 短期 scoped credential、魔数/解码校验、隔离区、安全检测 |
| 重复请求/竞态 | Idempotency-Key、唯一约束、事务锁、乐观锁、Outbox |
| 敏感日志/埋点泄漏 | 字段白名单、日志脱敏、正文/URL/token 禁止、访问分级 |
| 第三方审核/AI 数据留存 | 服务端代理、供应商合同与删除策略、最小输入、审计；AI 延后 |
| 身份绑定/账号合并劫持 | 绑定前近期认证 + provider proof；冲突不自动合并；操作审计与撤销窗口 |

## 13.2 按需授权清单
| 能力 | 触发时机 | 拒绝降级 | 记录 |
| --- | --- | --- | --- |
| 选择图片/视频 | 用户点击添加媒体 | 继续纯文字记录 | 同意状态，不记录相册内容 |
| 保存相册 | 用户点击导出 | 提供稍后重试/应用内查看 | 导出动作审计 |
| 订阅提醒 | 用户主动开启具体提醒 | 应用内消息完整可用 | 模板/场景/结果 |
| 分享 | 用户点击分享并确认披露清单 | 保存草稿/相册 | 分享产物版本，不记录接收人 |
| App 推送 | 用户在 App 内开启具体提醒 | 应用内消息仍完整可用 | installation、provider、场景、结果；不记录通知正文 |

## 13.3 内容安全
- 文本在发布、短评、回顾编辑时检测；媒体上传后异步检测。高风险内容不可 SHARED、生成或分享。
- 审核供应商结果映射为内部 PASS/REVIEW/BLOCK，保存 reason_code 和模型/规则版本，不保存不必要的原始响应。
- 申诉创建独立 case，只有最小授权人员可访问隔离内容；所有查看和处置写审计。
- 审核超时默认不向另一半开放；作者看到处理中状态并可删除。安全失败不返回敏感命中词细节。
## 13.4 审计
| 必须审计 | 字段 |
| --- | --- |
| 配对/接受/撤销/解绑 | actor, target, relation_version, result, reason, request_id, time |
| 可见范围变化 | moment_id, old/new visibility, actor, version |
| 删除/恢复/注销/导出 | scope, request_id, step status, object count bucket |
| 敏感记录主动加入回顾 | recap/snapshot/moment, actor, rule_version |
| 后台查看/申诉处理 | operator, case, purpose, action, time |

## 13.5 删除、备份与注销
1.  普通删除立即撤销他人访问并进入 30 天回收站；到期生成 PURGE 任务。
2.  PURGE 按数据库派生关系删除展示副本、模板图、回顾引用和对象；保留最小不可逆审计。
3.  注销先撤销会话、冻结关系、禁止新写入，再按步骤处理本人记录/媒体、互动、导出和第三方副本。
4.  备份不做随机单条删除，按既定滚动周期过期；恢复演练必须防止已删除数据重新对用户可见。
5.  用户可查询 deletion_request 进度；失败进入人工工单但访问权限保持撤销。
## 13.6 密钥与供应链
- AppSecret、对象存储密钥、审核供应商密钥进入 KMS/Secret Manager，不写代码、镜像或客户端。
- 服务账户按环境/服务拆分最小权限；生产数据禁止开发账号默认访问；密钥定期轮换。
- 依赖锁版本、生成 SBOM、执行 SAST/依赖漏洞/镜像扫描；高危漏洞阻断发布。
- CI 只使用短期部署身份；生产变更和数据修复需审批、审计和回滚方案。

## 14.6 灾备与恢复
- 定义 RPO/RTO 前需业务确认；建议数据库启用同地域高可用和按时间点恢复，定期恢复演练。
- 对象存储版本/跨区域复制按隐私与成本决策；删除语义必须覆盖副本与生命周期。
- Redis 缓存可重建；会话丢失可要求重新登录但不得丢草稿；队列消息由 Outbox 可重投。
- 恢复后先校验 couple/status、删除 tombstone 和授权版本，防止旧备份造成权限回退。

# 16. 风险、取舍与待决策
## 16.1 关键架构取舍
| 决策 | 选择 | 理由 | 后续演进 |
| --- | --- | --- | --- |
| 单体 vs 微服务 | 模块化单体 + Worker | MVP 团队规模下事务/交付更简单，域边界仍明确 | 媒体/回顾任务量独立增长时拆服务 |
| 客户端 vs 服务端模板渲染 | 客户端预览 + 服务端最终渲染 | 预览快、最终一致且可离开页面 | 成本过高可按模板/设备灰度客户端最终产物 |
| JWT vs 完全有状态会话 | 短 access token + 可撤销 session/version | 兼顾无状态请求与注销/风控即时失效 | 规模扩大可引入网关会话服务 |
| offset vs cursor | 三元组稳定 cursor | 新增记录时不漂移，符合 PRD | 搜索场景可另建检索游标 |
| 关系后删除 vs 先撤权 | 先 FROZEN 撤权，后异步隔离 | 用户隐私立即生效且耗时任务可恢复 | 保持该不变量，不因性能放松 |
| 统一后端 vs 端专属后端 | 统一领域 API + 渠道适配器 | 避免用户、关系、权限和内容规则分叉；满足多端数据一致 | 仅在流量/团队边界成熟后按业务域拆服务，不按客户端拆 |
